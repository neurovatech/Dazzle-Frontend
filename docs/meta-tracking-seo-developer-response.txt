IMPORTANT ARCHITECTURE GAP — please read before reviewing anything else
--------------------------------------------------------------------------
Your target architecture puts Meta CAPI entirely on the ASP.NET backend. That
is NOT what this repo currently does. This Next.js app has its own
server-side CAPI call (src/lib/analytics/metaConversionsApi.ts, called from
src/app/api/analytics/purchase/route.ts) that talks to Meta's Graph API
directly, using its own server-side access token
(META_CAPI_ACCESS_TOKEN env var on the frontend host).

This predates your handoff doc — it was built to cover Purchase tracking in
the absence of a backend CAPI service. It is functionally a stand-in for the
box in your diagram labeled "ASP.NET Backend → Meta CAPI", not the real
thing, and it has real gaps your doc explicitly warns against — see section
10.2 below.

Also relevant: per docs/tracking-backend-requirements.txt (an earlier,
separate handoff to the backend team), the ASP.NET backend ALREADY receives a
trackingMeta.eventId on every create-order-invoice call. If the backend team
has since built their own CAPI call from that field, then BOTH this Next.js
relay and the ASP.NET backend are sending Purchase to Meta right now. Because
they'd use the same event_id, Meta would deduplicate them (no double-counted
conversions), but it means two access tokens and two logs doing the same
job. Please confirm with the backend team whether they are already sending
CAPI Purchase events, and if so, plan to retire one side (recommended: keep
ASP.NET's, retire this Next.js relay) rather than running both indefinitely.

IMPLEMENTATION NOTE — why a hostname check instead of APP_ENV
--------------------------------------------------------------------------
Your doc suggests `APP_ENV=production` as an environment variable gate. We
did not use that pattern, for a concrete reason: this app is heavily
optimized for Next.js static rendering (most pages are prerendered/ISR, not
server-rendered per request — see docs/PERFORMANCE-AUDIT-BN.md for the full
performance work this session). Reading the real request in a Server
Component (which `APP_ENV` checked via headers()/cookies() would require, if
you wanted it to vary the rendered HTML) would force pages back to dynamic
rendering, undoing that work.

A pure build-time `NEXT_PUBLIC_APP_ENV` env var (no headers() needed) would
avoid that problem, but introduces a different one: if it is ever left unset
on the production deploy, ALL tracking goes silently dark on production with
no error — worse than the staging-leak problem it's meant to prevent.

Instead: every tracker's inline script checks `location.hostname` in the
VISITOR'S BROWSER at the moment it runs (src/lib/analytics/environment.ts,
`guardProductionOnly()`), against an allow-list of
["dazzle.com.bd", "www.dazzle.com.bd"]. This is correct regardless of
deployment topology, needs no new environment variable anywhere, and was
verified live (see section 1 above). If your team specifically needs an
APP_ENV-style variable for other reasons (e.g. the backend), that's fine and
independent of this frontend mechanism.

7. Payload shape
  PARTIAL. Every event's actual payload is close to your suggested shape
  (content_ids, value, currency, contents with id+quantity+item_price, etc.)
  but is not literally typed as the eventName/eventId/eventTime/source/
  pageUrl/contentType TypeScript interface in your doc. No separate types.ts

8. Event ID / deduplication — CRITICAL, fixed a real bug here
  Before this work: bKash/SSLCommerz Purchase used a RANDOM event_id
  generated fresh on every page load of the payment-result page. Reloading
  that page after a successful payment fired a SECOND Purchase (browser
  pixel AND the server CAPI relay) with a DIFFERENT event_id — a genuine
  duplicate that Meta could not deduplicate, because your own rule ("do not
  use a new random ID on every thank-you-page refresh") was being violated.

  Fixed: trackPurchase() (pixelEvents.ts) now derives a STABLE event_id from
  the order id (`purchase_<orderId>`) when no explicit id is passed, and
  persists a "this order's Purchase was already fired" flag in localStorage
  (keyed by orderId, never cleared) — a reload now returns `null` and skips
  both the browser pixel call and the server relay call entirely. Verified
  by code review of both call sites
  (Cart/CheckoutPageCom.tsx, PaymentResult/PaymentResultView.tsx); not yet
  verified against a real duplicate-reload in a live browser session (would
  need a real test order).

9. fbp/fbc/click-id capture
  DONE (pre-existing, unchanged) — src/lib/analytics/clickIds.ts.
  em/ph SHA-256 hashing
  DONE in metaConversionsApi.ts's server code, but the frontend never
  actually collects/sends email or phone today — nothing on this frontend
  passes em/ph into the CAPI call. If you want better Meta match quality via
  hashed customer email/phone, that requires either (a) the frontend passing
  the logged-in customer's email/phone to the CAPI relay, or (b) the ASP.NET
  backend adding it when it owns CAPI. Flag if you want (a) done here.
